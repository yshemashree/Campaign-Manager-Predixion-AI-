# 3. Tech Stack and Key Decisions

> Each decision lists the options we considered, why the winner won, **the trade-off we knowingly accept**, and **when we'd choose differently**. If you can explain the last two columns, you understand the decision rather than having memorised it.

## 3.0 The stack at a glance

| Layer | Choice | One-line reason |
| --- | --- | --- |
| Architecture style | **Modular monolith**, 2 process types (API, worker) | One domain model, no distributed transactions, processes split only where the runtime behaviour differs |

## D0. Build our own execution engine, or adopt a job framework?

This is the most important decision. The engine must give us, **at the same time**:

1. a **global per-org** rate limit (across processes and machines) plus a per-campaign pace,
2. **instant pause / resume / stop** of work that is already "queued",
3. **delayed work** (retries, windows) that can be cancelled or moved,
4. **per-contact state** that the UI can query and filter live,
5. **no duplicate dials** after crashes.

| Option | (1) global per-tenant limit | (2) instant pause/stop | (3) movable delayed work | (4) queryable per-contact state | (5) crash semantics | Ops weight | Verdict |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **Celery** (Redis/RabbitMQ broker) | ❌ `rate_limit` is **per worker instance**, not global | ❌ queued messages keep running; needs check-and-drop | ⚠️ ETA tasks sit in worker memory; with the Redis broker, ETA beyond the visibility timeout is **redelivered, i.e. executed twice** | ❌ separate store needed | ⚠️ at-least-once ⇒ double calls | medium | Rejected: its rate limit and redelivery semantics are exactly the traps this assignment probes |
| **BullMQ** (Node) | ⚠️ OSS limiter is per queue; per-group (per-tenant) limits are a **paid Pro** feature | ⚠️ pause is per queue, not per campaign | ✅ delayed jobs | ❌ separate store needed | at-least-once | low | Rejected: would force Node and still not fit per-org limits |
| **RabbitMQ** | ❌ none | ❌ can't remove a message from the middle of a queue | ⚠️ needs the delayed-message plugin or TTL+DLX tricks | ❌ | at-least-once | medium | Rejected |
| **Kafka** | ❌ none | ❌ log is append-only | ❌ no per-message delay | ❌ | offset-based, replays | high | Rejected: built for streams, not scheduled per-item work |
| **Temporal** | ✅ server-side task-queue rate limits | ✅ via signals | ✅ durable timers | ⚠️ via its own visibility store | ✅ excellent | **high** (server + its DB + UI) | Strong, but overkill: 1M contacts = 1M workflows, a heavy "single command" stack, and the brief explicitly asks *us* to design queueing/workers/windows |
| **Redis-only queue** (sorted sets by due time) | ✅ with Lua | ⚠️ must remove/move members | ✅ | ❌ Redis becomes the source of truth for state | ⚠️ AOF `everysec` can lose the last second ⇒ "was this called?" is forgotten | low | Rejected: durability plus dual-write consistency with Postgres |
| **Postgres rows as queue + Redis gate + own workers** ✅ | ✅ Redis Lua gate | ✅ nothing is pre-queued; the gate flips | ✅ `next_attempt_at` column | ✅ it *is* the table | ✅ leases + send markers + unique constraints | **low** (PG + Redis we need anyway) | **Chosen** |

**Trade-offs we accept:** we write and test about 500 lines of engine code ourselves (slot loop, scheduler, reaper, Lua scripts). A Postgres queue costs polling plus write amplification, which matters around several thousand dials/s per node, well above our needs.
**This pattern is proven:** Postgres-backed queues run in production at many companies (pg-boss, Oban, River, Solid Queue, GoodJob, graphile-worker, Procrastinate all use `SKIP LOCKED`).
**When we'd revisit:** at sustained 10k+ dials/s, move the hot queue into Redis Streams with an outbox from Postgres, or partition/shard Postgres by org.

## D1. Architecture style

| Option | Pros | Cons | Verdict |
| --- | --- | --- | --- |
| **Modular monolith** (API + worker processes, one codebase) ✅ | One domain model and migration set; in-process calls; simple local setup; easy to reason about | Must keep module boundaries disciplined | **Chosen** |
| Microservices (campaign svc, cohort svc, dispatcher svc...) | Independent deploys and scaling | Network hops, distributed transactions, N deploy pipelines, a harder demo; no team-size reason | Rejected for this scope |
| Serverless (functions + managed queues) | No servers | Cold starts break precise pacing; long-lived loops don't fit; no "single command local setup" | Rejected |

**Accepting:** the API and worker deploy together. **Revisit when:** separate teams own separate parts, or one part needs a different runtime (e.g. rewriting only the dispatcher in Go; the SQL + Lua contract makes that possible).

## D2. Backend language and framework

| Criterion | **Python + FastAPI** ✅ | Node + NestJS/Fastify | Go (chi/echo) | Java 21 + Spring Boot | Django + DRF |
| --- | --- | --- | --- | --- | --- |
| Concurrency model for I/O-bound work (HTTP to Sarvam, DB, Redis) | asyncio + uvloop: thousands of sockets per process | event loop: same | goroutines: best in class | virtual threads: good | sync-first; async ORM partial |
| Raw CPU speed | lowest | medium | high | high | lowest |
| **Does CPU speed matter here?** | No. The ceiling is Sarvam's rate limit (≤500/s per campaign), and one Python process can drive far more HTTP calls than that | | | | |
| OpenAPI (a deliverable) | **auto-generated from type hints** | decorators, good | needs codegen/annotations | springdoc, good | drf-spectacular, good |
| Request validation | Pydantic v2 (Rust core) | zod / class-validator | manual + libraries | Bean Validation | serializers |
| Domain libraries (phones, time zones, CSV) | `phonenumbers`, `zoneinfo`, `csv` (stdlib) | libphonenumber-js, luxon | ports exist | libphonenumber (original), `java.time` (excellent) | same as Python |
| Delivery speed for one developer | **very high** | high | medium | medium-low | high (but sync) |
| Ecosystem traps for this problem | Celery's per-worker rate limit (we avoid Celery) | BullMQ per-group limits are paid | none, but you build everything | none | Celery again |
| Shares a language with the frontend | no | **yes** | no | no | no |

**Why Python + FastAPI:** the workload is I/O-bound and externally rate-limited, so we trade raw speed (not needed) for delivery speed, strict validation and free, always-correct OpenAPI docs.
**Accepting:** no shared types with the frontend by default. We fix this by **generating TypeScript types from the OpenAPI spec** (`openapi-typescript`), so the contract stays single-sourced.
**Revisit when:** a single dispatcher process needs >5k dials/s, or the team is TypeScript-first (then NestJS + the same architecture).

## D3. Database

| Option | Pros | Cons | Verdict |
| --- | --- | --- | --- |
| **PostgreSQL 17** ✅ | `FOR UPDATE SKIP LOCKED`; **partial indexes** (our queue index); JSONB for agent variables and policies; `COPY` bulk load; `timestamptz`; mature transactions; RLS for tenant isolation | Vertical scaling first; needs autovacuum care on hot tables | **Chosen** |
| MySQL 8 | Has `SKIP LOCKED`; widely known | **No partial indexes**; weaker JSON indexing; no `COPY` (`LOAD DATA` is often disabled) | Rejected |
| MongoDB | Flexible documents; atomic `findOneAndUpdate` claims | Relational tenancy, reporting and constraints (e.g. `UNIQUE (campaign_id, phone)`) are harder; transactions are an add-on | Rejected |
| DynamoDB / Cassandra | Massive scale | No ad-hoc queries for dashboards; complex conditional-write modelling; not local-friendly | Rejected (wrong scale) |

**Accepting:** one primary is the write bottleneck (estimated about 4k writes/s at the 1,000 dials/s target, fine). **Revisit when:** sustained write load nears a single node's limit → partition `contacts`, then shard by org.

## D4. Coordination store (where the rate gate lives)

| Option | Atomic? | Latency | Shared clock | Fit | Verdict |
| --- | --- | --- | --- | --- | --- |
| **Redis + Lua** ✅ | ✅ scripts run atomically (single-threaded) | sub-ms | ✅ `TIME` inside the script | Built for exactly this; also gives pub/sub, TTL locks, counters | **Chosen** |
| Postgres row / advisory lock as limiter | ✅ | 1–5 ms + row-lock contention on one hot row | ✅ `now()` | Works at low rates; adds load to the database we most need to protect | Rejected |
| etcd / ZooKeeper | ✅ (consensus) | ms, write-heavy is costly | n/a | Built for config/leader election, not thousands of counter updates per second | Rejected |
| In-process limiter per worker | ❌ budgets add up across workers | n/a | ❌ | **This is the bug the assignment is testing for** | Rejected |
| Rely on Sarvam returning 429 | n/a | n/a | n/a | A rejected request still counts as a hit, so the limit is already broken | Rejected |

**Accepting:** Redis is a hard dependency for *dispatching* (by design we fail closed without it). **Revisit when:** Redis CPU saturates → Redis Cluster (keys are already hash-tagged per org).
*Note:* Valkey (the BSD-licensed Redis fork) is a drop-in alternative if licensing matters.

## D5. Rate-limiting algorithm

The requirement is "at most N per second", and we read it strictly: **in any rolling 1-second interval**.

| Algorithm | Can it exceed N in a rolling second? | Memory | Burst shape | Coordination cost | Verdict |
| --- | --- | --- | --- | --- | --- |
| Fixed window counter | **Yes, up to 2N** at window boundaries | O(1) | bursty | 1 op | Rejected |
| Sliding window counter (weighted) | **Yes** (it's an approximation) | O(1) | bursty | 1 op | Rejected |
| Token bucket (burst = N) | **Yes, up to ~2N** (full bucket + refill) | O(1) | bursty | 1 op | Rejected |
| Sliding window log | No (exact) | O(N) per org | **N at once**, then wait | polling herd when saturated | Viable runner-up |
| **GCRA (virtual scheduling), burst = 1, with reservations** ✅ | **No.** Grants are ≥ T apart (proof in `02` §B.5) | O(1) | **evenly spaced**, accepted by any downstream limiter | **1 call per dial, no polling** | **Chosen** |

Why "with reservations": instead of "denied, try again" (which makes every waiting worker hammer Redis at each boundary), the gate **books the next free slot** and says *"send at +140 ms"*. One script call per dial, zero herd. Why the **safety margin**: it makes the guarantee hold at *Sarvam's* side, not just ours, despite jitter (about a 5% throughput cost, configurable).

## D6. Real-time updates to the UI

| Option | Pros | Cons | Verdict |
| --- | --- | --- | --- |
| **Server-Sent Events** ✅ | Server→client push is exactly our need; plain HTTP (proxy- and LB-friendly); built-in reconnect + `Last-Event-ID`; trivial in FastAPI | One-way only; native `EventSource` can't send an `Authorization` header (we use a fetch-based SSE client); HTTP/1.1 limits ~6 connections per domain (HTTP/2 removes this) | **Chosen** |
| WebSockets | Bidirectional | We don't need client→server streaming; extra heartbeat/reconnect/auth plumbing | Rejected |
| Polling every N seconds | Simplest | Latency vs load trade-off; many viewers hammer the DB | Used **only as a fallback snapshot** (every 10 s) |

Pattern: **push for speed, pull for truth.** Pub/sub can drop messages, so a periodic snapshot corrects any drift.

## D9. Authentication, authorisation and secrets

| Topic | Choice | Alternatives and why not |
| --- | --- | --- |
| Session model | **JWT bearer** (short-lived) | Cookie sessions need CSRF handling and are awkward for REST clients. An external IdP (Keycloak/Auth0) is too heavy for this scope (fine to add later behind the same interface) |
| Password hashing | **argon2id** (OWASP's first recommendation) | bcrypt is fine but older; never plain SHA |
| Tenant isolation | Mandatory `TenantContext` in every repository call; 404 for foreign ids | Postgres Row-Level Security is a planned second layer (stretch) |
| Sarvam API keys | **AES-256-GCM** at rest; write-only API; decrypted only in workers | Plaintext in the DB is unacceptable; a cloud KMS is out of scope locally (the key comes from env) |
| Webhook authenticity | **HMAC of `attempt_ref` inside metadata** | Sarvam doesn't document signed webhooks; an IP allow-list alone is brittle |

## D10. Smaller choices

| Choice | Why | Alternative |
| --- | --- | --- |
| **httpx** | async, connection pooling, separate connect/read timeouts, clear exception types (we must tell "never sent" from "maybe sent") | aiohttp (slightly faster, clunkier API) |
| **phonenumbers** | Port of Google's libphonenumber: validation and E.164 formatting for every region | Regexes, which are wrong for real-world numbers |
| **zoneinfo** (stdlib) | IANA tz database, DST-correct | pytz (legacy API) |
| **stdlib csv, streaming** | Constant memory and precise per-row errors | pandas loads everything into memory and hides row-level errors |
| **UUIDv7 ids** | Time-ordered (index-friendly) and not guessable | bigint (enumerable), UUIDv4 (random inserts fragment B-trees) |
| **uv** | Very fast, lockfile, reproducible | pip-tools, Poetry |
| **ruff + mypy** | Lint + format + types in seconds | flake8 + black + isort |
| **Hypothesis** | Property tests find time-zone and window edge cases humans miss | Hand-picked examples only |
| **structlog + Prometheus metrics** | Machine-readable logs with ids; standard metrics format | print/logging; StatsD |
| **mock-sarvam** service | Load and fault injection without phoning real people; doubles as the **independent rate referee** for the demo | Only real calls, which would be costly, slow and unsafe to load-test |

## 3.11 Things we deliberately did not do (and why)

- **No Kubernetes, no service mesh.** Docker Compose is the required local deliverable, and the design is container-ready if someone deploys it later.
- **No Kafka / event sourcing.** Postgres plus an audit log gives us history without the operational weight.
- **No ORM magic on the hot path.** The claim, release and record queries are explicit SQL you can read and reason about.
- **No caching layer for business data.** Postgres answers fast enough. Redis is a cache only for 1-second stats.
- **No premature sharding.** One Postgres and one Redis cover the target with headroom. The scaling path is written down (`02` §B.20).
